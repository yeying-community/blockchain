# 审查检查清单(大模型应用开发)

给**人类审查者**用的辅助清单。逐项检查并写明发现,**最终的通过或驳回由人做出**。
模型辅助审查时,只输出发现和修改建议,不输出结论。

## 一、范围

- [ ] 内容在收录范围内?(没有攻击配方、模型排名、未公开内部细节的猜测)
- [ ] 层级放对了?变化快的内容(框架、接口、价格、某个模型版本的行为)没有放进基础层?
- [ ] 应用层写明了在什么环境、什么版本上验证过,截至何时?

## 二、事实与证据

- [ ] 每个事实性论断都有出处?出处真实存在、作者年份标题正确、内容与论断相符?(**模型容易编造出处,必须逐条核对**)
- [ ] 有没有把**某一家**模型或产品的行为写成**所有**模型的规律?
- [ ] 有没有把训练数据里的流行说法当成事实?(例:"一个 token 约等于 0.75 个英文单词"只是某些分词器在英文上的粗略经验)
- [ ] 数字说明了只是举例、因模型而异,并告诉读者怎么查到真实值?

## 三、可验证性

- [ ] "自己验证"一节的代码能运行?依赖写清楚了?实际运行结果与文中描述一致?(**请亲自跑一遍**)
- [ ] 调用模型的部分是可替换的,没有绑死某一家厂商?
- [ ] 没有提交密钥、令牌等敏感信息的示例写法?

## 四、可解释性(P1)

- [ ] 读者能明白"为什么",而不只是"怎么做"?
- [ ] 应用层每一步都对应到一条基础原理,并在"引用"中列出?
- [ ] 没有相关背景的开发者能读懂?术语都解释了,并给出英文原词?
- [ ] 符合"只讲一件事、自身能读懂"?

## 五、表述

- [ ] 没有夸大(彻底解决、最佳实践、一定能)?
- [ ] 有争议的问题写成了"认识之争",并列了各方证据,没有替读者下结论?
- [ ] 写清了会失效的情况?(漏写适用条件是最常见的表述不准确)

## 六、来源与核验要点

- [ ] 来源标注正确?模型生成的内容标为"模型生成",未标为"已核验"?
- [ ] 起草者列出的核验要点都逐条确认过?
