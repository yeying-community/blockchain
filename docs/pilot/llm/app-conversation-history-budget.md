# 按词元预算管理对话历史

| 字段 | 内容 |
|---|---|
| 层级 | 应用 |
| 主题 | 提示与上下文 |

| 版本 | v1 |
| 语言 | zh |

## 核心陈述

自己开发对话应用时,每次请求前都要决定"把多少历史放回上下文"。最简单可靠的做法是:
**固定保留系统提示和本次问题,给回答预留额度,剩下的预算从最近的一轮往前装,装不下就停**,
并且整轮(一问一答)保留或丢弃。

## 正文

### 怎么做

1. 确定三个数:模型的上下文窗口 `window`;给回答预留的词元数 `reserve_output`(不少于你设置的最大输出词元数);
   每条消息的格式开销(角色标记等,因模型而异)。
2. 先扣掉系统提示和本次问题;如果这一步就超了,说明系统提示或问题本身太长,应该报错,而不是悄悄截断。
3. 把历史按"一问一答"分成轮,**从最近的一轮往前**逐轮加入,直到预算用完。
4. 按时间顺序拼回:系统提示 → 保留的各轮 → 本次问题。
5. 记录丢掉了几轮(写日志或提示用户),方便排查"模型怎么不记得了"。

下面是一个只用标准库的最小实现(在 Python 3.12 上运行验证,2026-11):

```python
def count_tokens(text):
    """替换为你所用模型的分词器。默认用 UTF-8 字节数:对字节级分词器,
    词元数不会超过字节数,所以它是一个保守的上界(会浪费一些额度,但不会超)。"""
    return len(text.encode("utf-8"))

PER_MESSAGE_OVERHEAD = 8  # 每条消息的角色标记等开销,因模型而异,宁大勿小

def msg_tokens(m):
    return count_tokens(m["content"]) + PER_MESSAGE_OVERHEAD

def fit_history(system, history, question, window, reserve_output):
    """在 window 词元内装下:系统提示 + 尽可能多的最近几轮 + 本次问题,并给回答留出 reserve_output。
    history 是按时间顺序的 [user, assistant, user, assistant, ...]。返回 (messages, 丢掉的轮数)。"""
    fixed = [{"role": "system", "content": system}, {"role": "user", "content": question}]
    budget = window - reserve_output - sum(msg_tokens(m) for m in fixed)
    if budget < 0:
        raise ValueError("系统提示 + 问题 + 回答预留 已超出窗口,请缩短它们")
    turns = [history[i:i + 2] for i in range(0, len(history), 2)]  # 一问一答为一轮,整轮保留或整轮丢弃
    kept = []
    for turn in reversed(turns):  # 从最近的一轮往前装
        cost = sum(msg_tokens(m) for m in turn)
        if cost > budget:
            break
        kept.insert(0, turn)
        budget -= cost
    msgs = [fixed[0]] + [m for t in kept for m in t] + [fixed[1]]
    return msgs, len(turns) - len(kept)

if __name__ == "__main__":
    hist = []
    for i in range(1, 7):
        hist += [{"role": "user", "content": f"第{i}个问题" + "。" * 40},
                 {"role": "assistant", "content": f"第{i}个回答" + "。" * 40}]
    msgs, dropped = fit_history("回答一律用中文。", hist, "总结一下我们聊了什么", window=1200, reserve_output=300)
    used = sum(msg_tokens(m) for m in msgs)
    print(f"保留 {len(msgs)} 条消息,丢掉最早的 {dropped} 轮,占用 {used} 词元(上限 {1200 - 300})")
    print("第一条:", msgs[0]["role"], "| 最早保留:", msgs[1]["content"][:4], "| 最后一条:", msgs[-1]["content"])
    assert msgs[0]["role"] == "system" and msgs[-1]["content"] == "总结一下我们聊了什么"
    assert used <= 1200 - 300
```

### 为什么

- **为什么必须做这件事**:模型不保存对话,历史只能由应用每次重新发送;而上下文窗口有上限,历史迟早会放不下。
- **为什么按词元而不是按字数或条数**:窗口按词元计算;字数与词元数的换算因分词器和语言而异,按条数更是完全不可控。
- **为什么给回答预留额度**:输入和输出共用窗口,把窗口全用在输入上,回答会被截断或请求被拒绝。
- **为什么固定保留系统提示**:重要的约定放在系统提示里,才不会随着历史增长被截掉。
- **为什么整轮保留**:只留下回答而丢掉对应的问题(或反过来),模型会看到断裂的上下文,容易误解。
- **为什么从最近的往前装**:多数对话中,最近的内容与当前问题最相关。

### 常见错误

| 错误 | 为什么会出错 | 怎么纠正 |
|---|---|---|
| 按字数估算词元 | 换算比例因语言与分词器而异,中文、代码尤其不准 | 用所用模型的分词器计数;没有时用保守的上界(如 UTF-8 字节数) |
| 不给回答留额度 | 输入和输出共用窗口 | 预留不少于最大输出词元数 |
| 系统提示放在历史里一起截断 | 最早的消息最先被丢掉,约定随之失效 | 系统提示单独处理,永远保留 |
| 超出时让接口自己截断 | 不同接口超出时的行为不同,可能直接报错,也可能截掉你不想丢的部分 | 发送前自己控制 |
| 悄悄丢弃、不留记录 | 用户和开发者都不知道模型为什么"忘了" | 记录丢掉的轮数,必要时提示用户 |

## 自己验证

把上面的代码存为 `history.py` 直接运行(`python3 history.py`)。预期输出:

```
保留 6 条消息,丢掉最早的 4 轮,占用 634 词元(上限 900)
第一条: system | 最早保留: 第5个问 | 最后一条: 总结一下我们聊了什么
```

然后把 `count_tokens` 换成你所用模型的分词器,用你的真实对话数据测试:发送前计算的词元数,
与接口返回的实际用量(多数接口在响应里给出输入词元数)对比,两者应接近,且计算值不小于实际值。

## 适用范围与局限

- 适用:任何需要多轮对话的应用。
- 不适用 / 会失效的情况:早先内容对当前问题至关重要时,简单截断会丢掉关键信息,
  需要配合摘要旧内容、或检索相关的历史片段(待补应用单元)。
- 容易过时的部分:各模型的窗口大小与消息格式开销;部分接口开始提供服务端的历史管理。
- 默认的 `count_tokens`(UTF-8 字节数)只对字节级分词器是上界;对中文文本会明显高估,浪费额度,
  正式使用时应换成真实的分词器。

## 核验要点(给人类审查者)

1. 请实际运行代码,确认输出与"预期输出"一致。
2. "字节级分词器的词元数不超过字节数"——还要加上特殊词元;代码里的每条消息开销是否足以覆盖?
3. `PER_MESSAGE_OVERHEAD = 8` 只是示例,是否应提示读者如何测出自己所用模型的真实开销?
4. 一轮只按"一问一答"切分;遇到工具调用(一轮里有多条消息)时会出错,是否需要在局限中写明?
