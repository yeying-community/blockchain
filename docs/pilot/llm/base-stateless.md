## 核心陈述

模型在一次推理结束后,**不会记住这次对话**。聊天应用里模型"记得"前面说过的话,是因为应用**每次都把对话历史
重新放进上下文**一起发送。所谓"记忆",是应用层做的事,不是模型的能力。

## 正文

### 一次对话在接口层面是什么样

调用对话接口时,请求里通常带着一个消息列表:系统提示、用户第一句、模型第一句回答、用户第二句……
模型根据**这一次请求里**的全部内容生成回答。下一轮,应用把新的问答追加到列表末尾,**再把整个列表发一遍**。

如果第二轮请求只发"那它的首都呢?",不带前文,模型就不知道"它"指什么。

### 模型的参数在对话中不会改变

模型的知识存在训练得到的参数里。普通的推理请求只读取参数,**不修改参数**。你在对话里告诉它的新信息,
请求结束后就不复存在;要让它下次还知道,只能再放进上下文,或存到应用自己的数据库里、需要时取出来放回上下文。

### 对开发者意味着什么

1. **对话越长,每次请求越大**:历史在不断累积,词元数、费用、延迟都在增长,最终会超出上下文窗口。
2. **"记忆"功能都是应用实现的**:保存对话、摘要旧内容、检索相关的历史片段,本质上都是"决定把什么放回上下文"。
3. **服务端的缓存或会话功能不改变这一点**:一些接口提供会话管理或提示缓存,减少了重复传输或计算,
   但模型每次生成时依然要"看到"这些内容。
4. **不要假设模型会记住你没发给它的东西**,也不要假设它会忘记你发过的东西(在同一请求的上下文里,它都看得到)。

## 自己验证

用任意对话接口做两次请求(把 `call_model` 换成你所用的接口):

```python
def call_model(messages):
    """替换为你所用模型的接口调用,返回回答文本。"""
    raise NotImplementedError

# 第一次:带上前文
print(call_model([
    {"role": "user", "content": "我最喜欢的数字是 17。"},
    {"role": "assistant", "content": "好的,记住了。"},
    {"role": "user", "content": "我最喜欢的数字是多少?"},
]))
# 第二次:只发问题,不带前文
print(call_model([{"role": "user", "content": "我最喜欢的数字是多少?"}]))
```

预期:第一次能答出 17;第二次答不出(或者明确说不知道)。如果你用的是带"记忆"功能的聊天产品,
它能答出来,是因为产品替你把信息放回了上下文,而不是模型自己记住了。

## 适用范围与局限

- 适用:通过接口调用的大语言模型推理。
- 不适用:在线学习、持续微调等会更新参数的场景(不在普通推理请求中发生)。
- 容易过时的部分:各厂商的会话管理、提示缓存、记忆功能的具体形式。

## 核验要点(给人类审查者)

1. "服务端的会话功能不改变这一点"——有些接口在服务端保存对话、请求里不再需要带完整历史;
   表述是否准确区分了"传输层面不用重复发送"和"模型生成时仍需看到全部内容"?
2. "推理不修改模型参数"的出处待补,是否需要补充一本标准教材作为出处?
3. 本单元主题标为"提示与上下文"还是"模型原理"更合适?
