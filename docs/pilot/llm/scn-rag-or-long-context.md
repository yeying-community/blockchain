# 资料太多放不进上下文:检索增强,还是直接用长上下文

| 字段 | 内容 |
|---|---|
| 层级 | 场景 |
| 主题 | 检索与知识 |
| 来源 | 模型生成(Claude Opus 5.5) |

| 版本 | v1 |
| 语言 | zh |

## 核心陈述

要让模型基于你自己的资料回答问题时,有两条路:把资料**全部放进上下文**,或者先**检索出相关的部分**再放进去
(检索增强生成,RAG)。资料少、问题需要通盘理解时,前者简单可靠;资料多、更新频繁、每次只需要一小部分时,
后者更省、更可控。**先判断资料量与问题类型,再选。**

## 正文

### 处境

你有一批资料:产品文档、公司制度、代码库、几百份合同……希望模型基于它们回答,而不是凭训练时的印象。
模型训练时没见过这些资料,也不会因为对话而学会它们,所以资料必须在回答时放进上下文。

### 两种做法

| | 直接放进长上下文 | 检索增强生成(RAG) |
|---|---|---|
| 做法 | 每次把全部资料与问题一起发送 | 预先把资料切成片段、算好嵌入;提问时检索最相关的若干片段,只把它们放进上下文 |
| 前提 | 资料总量**放得进**上下文窗口,并留出提问与回答的余量 | 需要建立和维护检索系统 |
| 擅长 | 需要通盘理解的问题("这份合同有哪些对我不利的条款") | 答案集中在少数片段的问题("退款要几天到账") |
| 主要风险 | 越长越贵越慢;中间位置的信息可能被忽略 | **检索漏了,模型就看不到**,它可能据不相关的片段编造答案 |
| 资料更新 | 发送时就是最新的 | 要重新切片、重新计算嵌入 |

### 怎么判断

1. **算一算资料有多少词元**,和所用模型的上下文窗口比较。放不进,只能检索(或先筛选)。
2. **看问题类型**:需要综合全部资料的,倾向长上下文;"查一条事实"的,倾向检索。
3. **看成本**:同一批资料要被问很多次时,每次都发送全部资料可能很贵(有提示缓存的接口可以缓解)。
4. **两者可以结合**:先检索出较多的候选片段,再把它们全部放进一个较长的上下文。

### 不管选哪个都要做的事

- **准备一组带标准答案的问题**,比较不同做法的答对率,而不是凭感觉;
- **让模型说明答案来自哪个片段**,方便人检查;
- **资料里没有答案时,允许模型说"资料中没有"**,并在测试中专门测这种情况。

## 自己验证

拿你的真实资料和 20 个真实问题(其中几个在资料里**没有**答案),分别用两种做法回答,记录:答对率、
"资料中没有"时是否正确拒答、每次请求的词元数与耗时。

预期:没有放之四海皆准的答案。资料少时长上下文通常更省事;资料多时检索的成本优势明显,
但答对率高度依赖切片与检索的质量。

## 适用范围与局限

- 适用:基于私有资料的问答、客服、文档助手。
- 不适用:需要改变模型的语气、格式或掌握一种新技能的场景,这更接近微调要解决的问题(待补单元)。
- 容易过时的部分:上下文窗口越来越大、长上下文的价格在下降,两种做法的分界线会移动。
